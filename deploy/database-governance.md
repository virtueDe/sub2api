# 数据库压力治理

本文记录四阶段治理：统计限流与分量缓存、小时汇总、Gemini 生图持久化结算、连接预算隔离与故障采样。代码和迁移尚未部署，下面的本地验证不能替代生产灰度验收。已有 40 条历史扣费失败不自动补扣。

## 资源预算

- `internal/pkg/dbstats` 提供进程共享的重统计预算：同时 1 个，读取 2 秒，后台维护 30 秒。先准入，再申请连接/开启事务；槽占满返回 `STATISTICS_BUSY`，不在应用侧无限排队。
- 用量统计、用户/Key/管理员报表、趋势、榜单、聚合/重算、相关清理和图片利润结算共享该预算。管理员 `nocache` 只能绕过缓存，不能绕过仓库准入。
- 鉴权、余额、扣费、用量写入及调度配额读取不占此槽；已生成的利润报告读取、普通日志列表及其分页 COUNT 不在本次重统计预算内。它们仍需按真实热点观察。
- 第一阶段只有逻辑准入；第四阶段提供可选的物理隔离，见下文。单进程并发 1 不等于跨副本总并发 1；扩副本前必须重新分配数据库总预算。
- 后台长任务可能因新的 30 秒预算失败，需要观察聚合进度和错误；不要通过放大池/并发掩盖回填成本。第四阶段隔离会话进一步关闭统计 SQL 的并行 worker。

## `/v1/usage` 行为

先走原有余额/额度读取，再读取统计缓存。冷缓存只触发有界后台刷新，不等待重查询。

| 分量 | 成功缓存刷新间隔 | 旧快照最长保留 |
| --- | --- | --- |
| 累计 | 5 分钟 | 15 分钟 |
| 今日、每日趋势、模型统计 | 60 秒 | 3 分钟 |
| RPM/TPM | 20 秒 | 60 秒 |

`statistics` 按分量提供 `state`（`pending`、`fresh`、`stale`、`unavailable`）、`updated_at` 和 `refreshing`。未就绪/超出最大年龄时省略该分量，不返回伪零；成功的空列表/零统计仍正常返回。不同分量不承诺同一时间截面。余额不进入统计缓存。

模型显式日期范围分别缓存；默认滚动窗口按窗口类型共享缓存，元数据 `range_start`/`range_end` 表示上次计算实际使用的区间。今日分量按服务器自然日隔离，跨午夜的在途结果丢弃。

最多 1024 个缓存条目、64 个待刷新任务、一个按需启动的 worker；排队超过 10 秒丢弃。单次刷新 2 秒；真实错误按 Key/分量退避 30 秒（切换日期也不能绕过），预算忙碌退避 1 秒。失败不推进成功快照时间。

查询页面展示每个分量状态和更新时间。仅在准备中/刷新中时进行最多 5 次后续拉取（2、4、8、16、30 秒间隔），完成、出错、切换 Key/范围、离开页面后停止；不会常驻轮询。

`database.statistics_budget`、`usage.statistics_cache`、`usage.statistics_refresh_failed` 各自至多每分钟输出一次，包含累计计数或脱敏错误类别，标记 `ops_system_log_skip=true`，不写回系统日志表。

## 有界故障采样

在 Linux 主机手动运行，示例：

```sh
python3 deploy/db_pressure_sampler.py \
  --postgres-container sub2api-postgres \
  --duration 120 --max-mib 20 \
  --output /tmp/sub2api-pressure-20261109.jsonl
```

工具只读，不安装后台服务、不改变 PG 参数。输出路径必须不存在，独占创建且权限 0600。最长采样窗口 900 秒、最大文件 100 MiB；结束会等待至多约 3 秒的在途数据库客户端调用，`/proc` 读取和进程调度时间另计。文件预留结束记录空间。

- 每秒：主机 CPU、内存、PSI、diskstats；最多 20 个有 CPU 活动的进程和 20 个 D 状态进程，记录 CPU 增量、RSS/内存分类、I/O 字节增量、宿主/namespace PID。权限不足的字段可能缺失。
- 数据库：每次采样结束后至少间隔 3 秒；只读会话，单语句 1 秒、客户端 3 秒超时；容器内另用 `timeout -s KILL 2` 限制 psql 进程。
- 记录会话 PID、等待事件、SQL 类别、查询/事务年龄；仅对锁等待查询 blocker。不会保存 SQL 原文、连接错误原文、请求内容、cmdline 或 environ。
- `visibility=own_role_only/unknown` 表示观测可能不完整，不能把空 activity 解读为数据库完全空闲。完整观测需要现有角色具备 `pg_read_all_stats` 或超级用户权限；工具不授予权限。
- Docker 模式依赖容器现有 `sh`、`timeout`、`psql` 和 `POSTGRES_USER/POSTGRES_DB`；缺失时显式记录失败。直接 psql 模式沿用环境/pgpass，不将凭据输出到采样文件。

该工具用于宿主进程与数据库 PID 关联采样；第四阶段的应用内环形缓冲不能替代它。手动采样文件保留由操作人员管理。

## 第二阶段：Key/用户小时汇总

迁移 `251` 建立 UTC 小时桶、追加式变更事件和显式回填清单。INSERT 批量去重；UPDATE 的旧/新 transition table 覆盖跨月移动；DELETE（含外键级联）登记旧桶。业务写入只追加标识，不锁统计总额行。后台每秒最多重算一个小时，以覆盖写替代累加，仅删除本批已领取事件；低 ID 晚提交仍保留待处理。

`database.usage_rollup_enabled` 默认 true，后台受阶段一共享预算限制；`database.usage_rollup_reads_enabled` 默认 false，先影子回填。`database.usage_rollup_read_key_ids` 非空时仅列出的 Key 走新读路径，用户汇总保持旧路径；空列表表示切换全部已覆盖查询。未回填完成、有当前身份待处理事件或发现对账差异时返回 `STATISTICS_BUILDING`，不伪造零值，也不自动放开明细扫描。

每分钟在同一 MVCC 快照抽查一个已完成小时，比较所有 Key/用户的请求数、Token、numeric 金额、耗时总和/计数，包含缺失和多余桶。有新事件时标记 `not_caught_up`；真实 `mismatch` 将 `usage_key_rollup_state.integrity_failed` 置 true，所有副本停止汇总读取。此标记不能自动清除，需修复、重新对账后由受控运维流程恢复。观察 `usage.rollup_progress` 的待回填小时、事件数和最老事件年龄，目标延迟不超过 60 秒；超标时回填降优先级，不增加并发。

受管分区创建与触发器安装同事务；删除分区先冻结分区写入并登记受影响桶，再删除，同事务提交。TRUNCATE 明确拒绝。禁止绕开应用维护路径直接 CREATE/ATTACH/DETACH/DROP 分区；数据库管理员手工 DDL 不由本迁移自动拦截。

累计和区间统计读取完整小时桶，非整点起止只读边界明细。日趋势仅在整小时偏移时区启用桶读取；半小时/45 分钟时区、模型/平台等未保存维度仍走受预算保护的原查询。用户 dashboard 的平台分项也仍使用原统计。不能声称所有报表已消除历史扫描。

切换顺序：保持读开关关闭 → 回填完成且事件延迟稳定 → 小范围对账无差异 → 配置少量 Key 并启用读开关 → 观察统计可用率和扣费等待后逐步放开。关闭读开关即可回退到阶段一的受限路径；保留触发器、事件和明细。停 worker 不停事件捕获，会产生积压，不能长期只关 worker。

本地 Docker 已恢复可用。真实 PostgreSQL 测试通过：首次历史回填、未就绪拒绝、部分小时边界、两种 NULL 耗时口径、跨分区改时间/身份、直接叶分区写入、新分区触发器、低 ID 晚提交及对账差异熔断；分区清理单测通过。这里只是本地正确性证据，尚无生产回填速度或峰值延迟验收结果。

## 第三阶段：Gemini 生图持久化结算

`database.usage_settlement_enabled`（环境变量 `DATABASE_USAGE_SETTLEMENT_ENABLED`）默认 false。首批覆盖 Gemini native 入口与经该入口执行的兼容图片请求，包括 n>1 的每个 native child；不宣称所有供应商、流式协议和既有异步任务都已改造。每个 child 在首次上游调用前创建独立 `settlement:` 身份，failover 保持身份不变；建档失败返回 503，不继续请求上游。

上游返回后同步计算并保存最终 command、价格/倍率/用量快照，最多三次有界保存尝试；这一步不经过可丢弃的用量队列。保存后的金额与原始 fingerprint 不可变。`ready` 恢复直接重放原命令，不重新查价、不重新生成图片。dedup、余额/订阅/Key/账号/平台额度、真实金额 usage log、`charged` 状态在同一事务内提交。提交结果不明可重试，不重复扣费；不会先插入永久的零费用占位日志。

缓存处理采用可重试失效，完成后才标记 `complete`；认证失效同时进入已有事务 outbox。新模式下平台额度写入并入通用扣费事务，同用户其他普通请求也不再依赖 Redis sentinel 决定是否写 DB，提交及重复确认均尝试失效旧缓存。必须关闭 `database.user_platform_quota_flusher_enabled`，平台配额准入以 DB 为准，读取失败明确拒绝。

首次启用时在 settings 写入内部标记 `internal_usage_settlement_db_quota_mode`，已有结算记录也会使启动进入此模式。关闭新请求开关、最后一个任务完成和重启都不会自动恢复 Redis 额度准入；这样普通请求在恢复期间产生的 DB 消费不会因旧缓存重用而漏计。该模式下启动 flusher 会被拒绝。此内部标记不是面板开关，不能直接删除来回退；回到旧模式必须另做全部副本停写、恢复任务清零、Redis 用量/脏集核对及清理的受控方案。本次不执行该回退。多副本必须统一该模式，不能让旧版本/旧 flusher 与新模式混跑。

Key、账号和订阅的周期用量使用保存的事件时刻；已进入较新窗口时不把旧费用计入新窗口，累计余额和总额度仍按固定金额结算。账号固定日/周窗口使用配置时区和重置小时，保留同窗乱序消费；滚动窗口保留原锚点。订阅在行锁保护下复用前检的日历日与 7/30 天推进规则，先推进过期窗口再累加，避免跨午夜完成的金额被后续重置清掉。平台日/周/30 天窗口同样不回退。变更配额策略或人工重置期间仍需核对历史窗口语义，不以恢复记录替代原始审计记录。

worker 每秒最多领取一项，失败约 30 秒后重试，已有金额的任务以数据库恢复后 5 分钟内追平为待验证目标。`created` 超过两小时仍无最终事实转 `needs_review/final_facts_missing`；价格计算失败也不会固化为免费成功。若进程在最终快照保存前退出，或数据库持续不可写，自动恢复不能推断金额，必须对账。`usage.settlement_needs_review` 和 `usage.settlement_recovery_failed` 是需要处理的告警。

恢复表只保存显式白名单的财务字段，最多 60 KB 输入，不保存账号关系对象、密钥、prompt、base64 或请求体。图片详情正常写在 usage_logs；n>1 批次结束后可独立补全全部输出。恢复路径若已丢失图片详情，只恢复财务记录，不伪造图片结果。关闭开关不删除结算或 dedup/archive；本轮不自动清理这些证据。

本地真实 PostgreSQL 验证覆盖：ready 后重建实例恢复、提交后未确认再重放、金额不可变、日志失败回滚余额及 dedup、未知事实转待核对、Key/账号/订阅/平台跨窗口恢复。已有 40 条历史失败没有新 intent，不会被此 worker 自动补扣。

## 第四阶段：物理隔离与故障证据

三个新配置均为启动时读取：

| 配置 / 环境变量 | 默认值 | 行为 |
| --- | --- | --- |
| `database.statistics_isolation_enabled` / `DATABASE_STATISTICS_ISOLATION_ENABLED` | false | 从原总连接预算划出 1 条统计读取、1 条统计维护 |
| `database.diagnostics_enabled` / `DATABASE_DIAGNOSTICS_ENABLED` | false | 启用应用内环形采样与故障文件 |
| `database.diagnostics_directory` / `DATABASE_DIAGNOSTICS_DIRECTORY` | 空 | 使用 `$DATA_DIR/logs/database-pressure`，未设置 DATA_DIR 则为 `data/logs/database-pressure` |

开启隔离时，`max_open_conns=50` 表示 **core 48 + read 1 + maintenance 1**，不是 52。总预算小于 3 拒绝启动。关闭隔离时两个统计入口复用 core，不增加连接。只有显式受治理的统计方法使用统计池；余额、鉴权、账务和写日志仍走 core。统计维护/小时回填/利润结算走 maintenance。已有日志列表及其 COUNT、未覆盖维度仍需按实际热点继续观察。

每条新 read 连接设置只读、`statement_timeout=2s`、`max_parallel_workers_per_gather=0`；maintenance 设置 `statement_timeout=30s`、并行 worker 为 0。两池均最多 1 条连接、连接建立超时 2 秒，仍受进程共享统计 gate 控制。单条慢统计不能借尽 core，但 core 的锁等待、磁盘压力和大日志写入仍可能影响扣费。此前 4 vCPU / 7.75 GiB 的生产规格不足以支持无证据扩大并行；本方案先减小统计成本和并发，不承诺通过加连接解决。

采样内容与界限：

- 每秒采样 core/统计池 DBStats 增量、统计 gate、扣费连接获取/事务/余额/额度/提交、用量日志 single/batch/fallback、系统日志批写及错误日志批写的固定标签计数和耗时桶。指标为累计值，可用相邻样本计算增量；不保留错误原文、请求内容或用户身份。
- 最近 80 个样本驻留内存。扣费失败，或核心池连续 3 秒出现等待/占满时触发；继续采集 20 秒后保存，至少间隔 60 秒。触发通道 8、文件队列 1，满时计数丢弃，不阻塞请求。停机可写出尚未集满的证据。
- 每 3 秒通过隔离 read 池尝试 PG 等待采样，750ms 上限；未隔离时显示 `not_sampled`，不额外借核心连接。最多 32 个活动/事务内会话，优先锁等待；多出会话显示 `Truncated`。每会话最多 16 个 blocker，记录总数和截断标志。只写固定 SQL 类别、PID、状态、等待及年龄，不写 SQL 原文。权限判断使用当前实际可用的监控权限，`own_role_only` 不能解释为全库没有等待。
- Linux 从挂载的 `/proc` 读取 CPU、内存、PSI、diskstats 和应用自身进程信息，每个文件最多 16 KiB并明确标记截断/不可用。宿主与容器范围未经验证，应用 PID 与数据库 PID 未自动关联；`postgres_process_cpu=unavailable`、`cgroup=not_sampled`。因此单靠此文件不能归因 PostgreSQL 进程的高 system CPU，仍需上面的宿主采样工具。
- 目录权限请求 0700，文件 0600；8 个固定 `incident-N.json` 槽，每份最多 2 MiB。超过编码预算会优先保留最新样本，并记录省略数量。8 个固定临时槽、独占创建及 rename 防止跟随最终路径符号链接。单 writer，不在业务请求上做文件 I/O。应把目录放在可写的持久卷，多副本使用各自目录以免争用槽位；监控 `FileFailures/DroppedFiles`，不能把“无文件”解释为无故障。

后台汇总、利润任务、恢复 worker、仪表盘异步刷新和 SQL 诊断探针均提供取消/排空与 Wire 清理，先停本次新增池的使用者再关池；写文件等待单独限时 2 秒。现有 HTTP 优雅停机仍只有 5 秒，超时后的所有长请求并未在本次全面改造成可排空，不应以此次后台清理承诺整个服务零中断升级。

## 灰度与验收顺序

诊断覆盖补充（本地实现，2026-11-14，尚未部署）：图片预留、退款和余额加载的依赖失败也触发上述有界故障文件，新增固定指标 `image_reserve`、`image_release`、`billing_load`、`payer_admission`。业务额度拒绝和用户取消不触发数据库事故；原错误链保持不变。图片失败记录在回滚/归还连接前采集，避免把清理时间误算到最后一条 SQL。

快照 `At` 表示实际开始采集，原定时器时刻另存 `ScheduledAt`；`FinishedAt`、`ElapsedMicroseconds` 和 `SchedulingDelayMicroseconds` 用于识别采集阻塞和调度延迟。Linux 各 `/proc` 项分别记录 `*_started_at`、`*_finished_at`、`*_elapsed_us`，PG 探针也记录实际起止和耗时。各来源仍不是原子快照，应按自己的区间关联；PG 的 `AgeSeconds` 是查询年龄，不能当作等待持续时间。新增记录不增加 SQL 探测频率，不替代宿主线程 CPU 和磁盘归因采样。

Linux 另保留 `/proc/vmstat` 中回收、内存规整、透明大页、换页和缺页计数的白名单；每秒只增加这一份最多 16 KiB 的读取。`scheduler` 复用 `cpu` 来源的采集区间，保留 `ctxt`、`processes`、`procs_running`、`procs_blocked`；`process_faults` 复用 `process_cpu` 区间，记录应用自身 minor/major faults，不包含子进程。两个派生项以 `*_source` 指向原来源，状态保留截断/不可用信息。缺失内核字段不补零，截断尾行不作有效计数。累计计数按相邻实际采样求增量；`procs_running/procs_blocked` 是瞬时数量。回收或规整计数上升只能定位相关活动，不能单独证明其 CPU 耗时；major faults 也不等同于 swap-in。

1. 先在预发布应用迁移 251/252，核对触发器开销、回填推进及存储增长；不删除历史明细、不重写 TOAST、不重启生产 PostgreSQL。本地约 102 万行 / 56 GiB TOAST 的调查说明图片大字段占用突出，但不能据此直接清理账务证据。
2. 保持汇总读和新结算入口关闭，启用统计隔离及诊断；每实例总池预算仍为 50。对比 core 等待、扣费/用量日志超时、统计拒绝与可用率、CPU/system/IO/PSI，覆盖真实高峰。若隔离引起统计不可用，先关闭隔离开关，保留逻辑 gate。
3. 汇总回填完成、持续对账一致、变更积压稳定后，先用 `usage_rollup_read_key_ids` 灰度少量 Key，再逐步开放；目标事件延迟不超过 60 秒，超标先限制回填，不加并发。读失败能明确显示未就绪，不退回无界扫描。
4. 所有副本完成升级、旧额度 flusher 停止且脏集完成核对后，才启用 Gemini 生图新结算。验证数据库短暂不可用、提交结果不明、Redis 失效失败、重启恢复及 n>1；恢复已冻结金额的积压目标为 DB 恢复后 5 分钟内追平。该目标需要生产负载证明。
5. 回退新结算只关闭 intake，保留 marker、恢复 worker、DB 配额模式、结算表和 dedup；不可回滚到不理解这些记录的旧二进制继续接流量。历史 40 条请求另行人工对账，不在本次自动处理。

上线验收必须确认：扣费失败没有持续新增；任何新失败都有可核对的结算状态；统计不会占满 core；汇总与明细对账一致；故障文件能够区分连接排队、数据库锁等待与系统压力。若高 system CPU 再现但仍不能对应宿主进程/SQL/等待，根因分析仍未闭环。

## 生图持久化暂扣与顶栏展示（本地实现，尚未上线）

新开关 `database.image_billing_reservation_enabled`（环境变量 `DATABASE_IMAGE_BILLING_RESERVATION_ENABLED`）默认关闭。开启后，常规生图入口的余额/订阅预留先写数据库，写入失败不请求上游。GPT、Gemini、兼容生图、图片工具请求和 WebSocket 图片轮次复用该流程；Gemini 多图适配按每次原生生成独立预留与结算。Simple Mode 不扣用户余额，不参与暂扣。

- 余额用户：预估金额从 `balance` 移入 `frozen_balance`；结算事务一次提交实际扣款、幂等凭据、最小用量账单与结算状态。预估多余金额归还；按 token 计费的实际金额可能高于预估，差额按真实账单补扣，可能产生原有透支语义。预留不是硬性费用上限。
- 订阅用户：预留订阅额度和 Key 配额，不冻结钱包余额。顶栏“生图暂扣金额”只展示钱包暂扣，包含既有批量生图；不把订阅额度伪装成现金。
- 请求结束且没有成功图片的明确失败（包括 451、499、502、524、传输超时，以及 200 流内失败）自动释放暂扣；这是一项用户退款策略，不代表供应商没有产生内部成本。重试期间不退款；重试后成功、部分出图后断线及已进入结算的请求保留账务恢复保护。HTTP 成功头本身不等于出图成功，最终转发结果参与判断。尚未获得最终结果的进程崩溃等情形仍不能仅凭记录年龄推断失败；缺最终事实超过两小时转 `needs_review`。
- 图片详情使用有界后台队列，超时/队列满可缺失详情，但不撤销已提交账单。最小账单仍与扣费同事务，绝不以零费用占位替代成功扣费。
- 最终财务事实在 `pricing.data_dir/image-settlement-facts` 写入本地 `.pending` journal 后提交数据库；退款写库失败时在同一目录写入 `.release` 恢复记录，后台自动重试，无须逐笔审批。迟到退款只允许释放无最终账单的订单，不能覆盖已确认用量。单条最多 60 KB，目录最多约 10000 条；只含账务字段或退款请求标识，不含提示词、图片、Key 密钥或密码。该目录必须位于持久化卷，多副本各自保留自己的目录，容器替换不能丢掉它。文件 fsync 提供进程重启恢复；不宣称无断电风险。数据库和本地持久化同时失败或未收到最终结果时仍需核对，不能承诺任意故障下自动完成结算。
- 批量生图结算也改为原子事务；已生成但解析/写账失败保留暂扣继续重试。`uploading` 成为提交边界，提交响应不明时保留可见任务并标记 `PROVIDER_SUBMIT_OUTCOME_UNKNOWN`，不允许无上游任务号的直接取消退款；按年龄退款仅适用于尚未提交的 `created`。需要以批次 ID 核对供应商后再处理未知任务。
- 顶栏浮层和手机菜单显示“生图暂扣金额”，支持八位小数。打开时刷新，显示期间每 10 秒更新，关闭后停止；可用余额直接使用后端 `balance`，总余额为可用加暂扣，不再次减去冻结额。

部署前须应用迁移 253，确认持久化卷可写，并让所有应用副本的 `database.user_platform_quota_flusher_enabled=false`。首次启用后，平台额度以数据库为准的标记会持久保留；只关闭新请求开关不会停掉已有订单恢复，也不能自动切回 Redis 累加。批量结算与未知结果保护随新代码生效，不由新开关单独控制。
